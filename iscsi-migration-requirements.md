# Rook-Ceph to Synology iSCSI migration requirements

## Scope

This document describes the work needed to replace Rook-Ceph RBD storage with Synology iSCSI for Kubernetes persistent volumes. It excludes creating the new Synology storage pool and volume.

This is a workload-by-workload data migration, not a storage driver replacement. A bound Kubernetes PVC cannot change its StorageClass. Each Ceph-backed claim must be recreated on Synology storage and restored or copied.

The recommended provisioner is the [official Synology CSI driver](https://github.com/SynologyOpenSource/synology-csi). It creates a thin-provisioned iSCSI LUN for each dynamically provisioned Kubernetes volume.

## Current state

The current storage configuration is in `kubernetes/apps/rook-ceph/rook-ceph/cluster/helmrelease.yaml`:

- `ceph-block` is the default StorageClass.
- It uses Ceph RBD, ext4, immediate binding, volume expansion, and a `Delete` reclaim policy.
- `csi-ceph-blockpool` is the VolumeSnapshotClass and also uses a `Delete` policy.
- The block pool stores three replicas across the three Kubernetes hosts.
- Each host contributes `nvme0n1` as an OSD.

The live-state assessment found:

- About 109 `ceph-block` claims.
- About 123 GiB of bound data.
- About 60.4 GiB of application data.
- About 62.6 GiB in claims named as caches.
- A detached 51.6 GiB RBD image associated with an old `volsync-plex-src` snapshot.

Git contains 29 active application PVCs generated by the Volsync component and 18 other explicit `ceph-block` consumers. This gives 47 active desired Ceph-backed claim consumers visible in Git. The difference between 47 desired consumers and 109 live claims includes chart-generated claims, Volsync temporary claims, retained claims, and possible orphaned claims.

OpenEBS and existing NAS NFS storage are separate:

- CloudNativePG and several other workloads use `openebs-hostpath`.
- Immich and WordPress have static RWX NFS volumes.
- Media applications mount NAS directories directly over NFS.

Those storage paths should remain unchanged unless they receive a separate migration plan.

## Talos changes

Every schedulable Talos node needs an iSCSI initiator. The current `officialExtensions` list in `kubernetes/bootstrap/talos/talconfig.yaml` does not contain iSCSI support.

Add:

```yaml
systemExtensions:
  officialExtensions:
    - siderolabs/iscsi-tools
```

Then regenerate the Talos image schematic and machine configurations and perform a sequential `talosctl upgrade` of all three nodes. The extension supplies `iscsid` and `iscsiadm`, which the Synology CSI node plugin uses. A reboot is required because the extension becomes part of the Talos system image.

Talos documents this requirement in its [iSCSI storage guidance](https://docs.siderolabs.com/kubernetes-guides/csi/storage#others-iscsi).

All schedulable nodes must reach:

- The DSM API, normally TCP 5001.
- The iSCSI portal, TCP 3260.
- The same stable NAS address after a node, NAS, or switch restart.

The existing storage network is the natural path. The NAS already uses `172.20.0.1`, and the nodes use `172.20.0.2` through `172.20.0.4`. Both remaining Kubernetes hosts must retain access to that network. A direct NAS link to only one host would prevent the other host from mounting or recovering iSCSI volumes.

Multipath storage should not be assumed. The first-party driver documents a normal iSCSI portal, not a complete multipath configuration. Dual NAS interfaces would need a separate tested design before they could count as transparent path failover.

## Synology CSI deployment

Add a Flux-managed platform application, likely under `kubernetes/apps/synology-csi/`, containing:

- Synology CSI controller.
- Privileged node DaemonSet.
- CSI provisioner, attacher, resizer, and snapshotter sidecars.
- `CSIDriver` resource.
- StorageClasses.
- VolumeSnapshotClass.
- Service accounts and cluster RBAC.
- ExternalSecret containing the DSM connection configuration.

Store the DSM connection data in 1Password and expose it through External Secrets. The connection information includes:

- DSM address and HTTPS port.
- Dedicated DSM username and password.
- CA certificate and TLS server name if the certificate does not match the address.

The upstream documentation says the CSI account must belong to the DSM administrators group and have DSM application access. Use a dedicated account and remove permissions unrelated to CSI management.

### Upstream packaging

The first-party driver currently documents Kubernetes 1.20 or newer support, snapshots, expansion, and cloning. The repository's included Helm chart is marked `0.9.3-SNAPSHOT`, uses relatively old CSI sidecars, and is described as a local-development chart. It is not a normal published OCI chart that fits this repository directly.

Use a release-pinned first-party driver image and either:

- Pin upstream release manifests through Flux and apply local patches for secrets and configuration.
- Package the upstream chart as a controlled OCI artifact.

Do not point Flux at the upstream `main` branch or run Synology's install script outside GitOps.

## Kubernetes storage classes

Create the Synology StorageClass as non-default during migration. A representative configuration is:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: synology-iscsi
provisioner: csi.san.synology.com
parameters:
  protocol: iscsi
  dsm: 172.20.0.1
  location: /volumeN
  fsType: ext4
reclaimPolicy: Retain
allowVolumeExpansion: true
```

Use `Retain` during migration. Deleting a PVC then leaves its LUN available for manual recovery. A separate class with `Delete` may later suit disposable data, although regenerable caches are better placed on `openebs-hostpath` or NAS HDD storage.

Create a Synology VolumeSnapshotClass. The common snapshot controller already runs under `kubernetes/apps/volsync/snapshot-controller`, so the Synology deployment should not install another common snapshot controller. The Synology CSI deployment still needs its driver-specific snapshotter sidecar.

Do not make `synology-iscsi` the default class until every claim that relies on the current default has been inventoried and migrated.

## Repository changes

Update explicit `ceph-block` and `csi-ceph-blockpool` references in application PVCs and Helm values.

The Volsync defaults also require changes:

- `kubernetes/components/volsync/pvc.yaml`
- `kubernetes/components/volsync/local/replicationsource.yaml`
- `kubernetes/components/volsync/local/replicationdestination.yaml`
- `kubernetes/components/volsync/remote/replicationsource.yaml`
- `kubernetes/templates/volsync/claim.yaml`
- `kubernetes/templates/volsync/minio.yaml`
- `kubernetes/templates/volsync/r2.yaml`

These resources currently use Ceph for application PVCs, source snapshots, restore snapshots, temporary mover volumes, and cache volumes. Replacing only the application StorageClass would leave Volsync dependent on Ceph.

Remove Rook dependencies from application `ks.yaml` and `helmrelease.yaml` files after their PVCs have moved.

Change the default StorageClass annotation from Ceph to Synology only after the last implicit Ceph consumer has moved.

## Data classification

Do not migrate every live RBD image blindly. Classify each claim first:

- Application state must be restored or copied.
- Regenerable caches should be recreated on local or cheaper NAS storage.
- Metrics retention may be shortened or recreated when history is not worth moving.
- Orphaned claims should be confirmed and deleted.
- The detached 51.6 GiB Plex-related image needs an explicit keep-or-delete decision.

The proposed 238.3 GiB mirrored NVMe target would hold the current 123 GiB of bound data at about 52 percent usage. Requested PVC capacities, snapshots, restore staging, and future growth can still exceed the physical capacity. Thin provisioning delays physical allocation but does not create capacity. Configure Synology capacity alerts and preserve enough free space for snapshots and recovery work.

## PVC migration procedure

Use the following procedure for each application:

1. Classify its claims as application data, cache, metrics, or orphaned data.
2. Confirm that the latest local and R2 Volsync backups can be listed and restored.
3. Stop or quiesce the application so writes stop.
4. Run a final Ceph-backed backup.
5. Change the old PV's reclaim policy to `Retain` when rollback should preserve its RBD image. The current Ceph class uses `Delete`.
6. Create a new iSCSI PVC with enough capacity and the same access mode.
7. Restore through Volsync Restic or copy through a temporary pod that mounts both claims.
8. Preserve ownership, permissions, extended attributes, and application security context.
9. Point the application at the new claim.
10. Start the application and verify its data and behavior.
11. Run and restore a new backup from the Synology-backed claim.
12. Keep the old Ceph volume until the application has operated correctly for an agreed period.

For databases, stop writes or use an application-native database dump. An online filesystem copy does not guarantee transactional consistency.

A Synology snapshot cannot restore a Ceph snapshot. Kubernetes snapshots belong to their CSI driver and storage backend. Use Restic or a filesystem copy to move data between Ceph and Synology.

## Volsync migration behavior

The current Volsync resources use `copyMethod: Snapshot`. Their defaults name `csi-ceph-blockpool` and `ceph-block` directly.

During a mixed migration, a global replacement would break applications that remain on Ceph. Migrate each application with one of these approaches:

1. Keep separate per-application source and destination StorageClass overrides during migration.
2. Run the final Ceph backup, change that application's complete Volsync configuration to Synology, and explicitly trigger a new Synology-side restore.
3. Use `copyMethod: Direct` to restore into a precreated Synology PVC.

The current ReplicationDestination uses the constant manual trigger `restore-once`. Changing a StorageClass does not necessarily create a new restore. Its existing `latestImage` may still refer to a Ceph snapshot. The migration must change the manual trigger, recreate the ReplicationDestination, or use a direct restore into the target PVC.

## Pilot and verification

Before migrating applications, use a scratch PVC to verify:

- Dynamic LUN creation.
- Pod mount and filesystem formatting.
- Data checksum after pod deletion and rescheduling to another node.
- Clean detach from one node and attach to another.
- PVC expansion.
- Snapshot creation.
- Restore into another PVC.
- Volsync backup and restore.
- Node reboot behavior.
- NAS and storage-switch reboot recovery.
- Behavior during a temporary loss of the iSCSI network.

Migrate one small Volsync-protected application before Plex, Prometheus, Loki, or other important services.

For the Git changes, run the repository's normal offline checks:

```sh
mise x github:home-operations/flate@0.4.10 -- flate test all -p ./kubernetes/flux --no-progress
mise x github:home-operations/flate@0.4.10 -- flate diff hr --base <rev> -p ./kubernetes/flux --no-progress
```

## Rook removal

Keep Rook until all of these have been removed or intentionally archived:

- Ceph-backed PVCs and PVs.
- Ceph `VolumeAttachment` objects.
- Ceph `VolumeSnapshot` and `VolumeSnapshotContent` objects.
- Volsync temporary and cache PVCs.
- Detached RBD images.
- Application dependencies on `rook-ceph-cluster`.

The Rook Flux Kustomizations in `kubernetes/apps/rook-ceph/rook-ceph/ks.yaml` use `prune: false`. Removing the Rook directory from Git will not uninstall the live resources.

Use a controlled removal sequence:

1. Confirm that no application, Volsync resource, or snapshot still uses Ceph.
2. Remove Ceph CSI after the final RBD attachment and snapshot have gone.
3. Remove the CephCluster and confirm that its resources terminate.
4. Remove the Rook operator, CRDs, secrets, monitoring resources, and namespace.
5. Clean `/var/lib/rook` and Ceph signatures from the old NVMe OSD disks before reusing them.
6. Remove `kubernetes/apps/rook-ceph` and every Rook dependency from Git.

## Availability changes

This migration simplifies the Kubernetes hosts and removes Rook's memory, CPU, and disk overhead. It also permits `hp3` to be retired.

It reduces storage availability:

- Ceph currently stores three copies across three hosts.
- Synology RAID 1 protects against one NVMe failure.
- RAID 1 does not protect against NAS failure, DSM failure, switch failure, or loss of the iSCSI path.
- All Synology-backed stateful applications stop together during a NAS outage.
- iSCSI volumes formatted with ext4 should remain `ReadWriteOnce`.
- Existing `ReadWriteMany` data should remain on NFS.
- Synology snapshots remain on the same NAS and do not replace the existing independent R2 backups.

The main body of work is migrating and verifying the PVCs. Installing the CSI driver is the smaller part.
